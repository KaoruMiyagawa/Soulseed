# 2.7.6-F1：数据归属与本地身份验证

## 运行方式

当前身份提供方只认证本机安装的 `local` 用户。`users → characters → conversations → messages`
表达归属；角色所有权在数据库中，不能通过请求中的 user_id/owner_id 改变。
记忆、来源、变更日志、提案、应用日志和澄清都记录 character_id。
生活及联系沿用角色字段，消息投递必须指向同一角色的会话。

1. 用现有 Python 生成口令：`python -c "import secrets; print(secrets.token_urlsafe(32))"`。
2. 在本机未跟踪的 `.env` 设置 `SOULSEED_LOCAL_PAIRING_SECRET`，不要把值放进前端配置。
3. 按原方式将后端绑定 `127.0.0.1:8001`，前端使用 `127.0.0.1:5174`；两端也可统一使用 localhost。
   不要混用 localhost 与 127.0.0.1，否则浏览器的站点 Cookie 规则会阻止会话。
4. 网页输入口令换取 8 小时 HttpOnly、SameSite=Strict 会话 Cookie；不使用 localStorage。
   数据库仅保存随机会话令牌的 SHA-256 摘要。退出删除服务端会话。

口令未配置时，配对返回 503，数据接口返回 401。连续五次错误配对后暂停五分钟。
请求必须来自本地回环连接，Host 必须是 localhost/127.0.0.1/::1；浏览器 Origin 也必须匹配允许的前端地址。
即使误用 `uvicorn --host 0.0.0.0`，远程数据请求仍被拒绝。配置中的非回环 host 也会被拒绝。

该口令对应本地用户，不是多用户登录系统。会话固定绑定一个已核验属于该用户的角色；
角色切换需要重新配对，并再次核验所有权。未来增加身份提供方时可复用 users 和会话归属，
但当前没有注册、找回口令、跨网络 HTTPS 登录或角色创建界面。
本机操作系统账户、文件系统和能读取 `.env` 的进程仍属于信任边界。
轮换配对口令不会自动删除已经签发的会话；安全轮换应同时撤销 auth_sessions。

## 服务端授权

所有产品数据 API 必须先验证 Cookie 摘要、有效期及当前角色所有权。
角色路径必须与会话绑定角色一致。会话和记忆 ID 在角色范围内查找，跨角色返回 404。
客户端传入 ID 只是资源选择，不是权限凭证。
服务端用 ContextVar 传递已授权角色，SQLite 每个连接捕获该范围，查询显式使用 current_character()。
异步请求和同步线程不共享可变的“当前角色”全局变量。
写入触发器校验归属不可静默改变及跨角色引用；这是查询过滤之外的第二道约束。
所有内部维护和记忆恢复任务也必须显式进入相应 character_scope。

## Migration 12 与旧数据

迁移不猜测旧会话归属。历史投递曾允许跨会话操作，因此主动消息不是足够可靠的所有权证据。
默认所有没有明确确认的旧会话保持 character_id=NULL；消息和澄清关联原样保留。
这些记录保存在原表中，但不进入普通会话、记忆检索、澄清恢复或主动联系流程。
已有 big_fish 是本地默认角色；其他历史角色保持 owner_user_id=NULL、ownership_status=quarantined。

迁移前，操作者可以在**备份副本核对**后，明确提供已确认的会话归属清单：

```sql
CREATE TABLE legacy_conversation_ownership (
    conversation_id TEXT PRIMARY KEY,
    character_id TEXT NOT NULL,
    evidence TEXT NOT NULL CHECK (length(trim(evidence)) > 0)
);
-- 仅填写已人工确认的原会话 ID、原角色 ID 和确认依据；不要批量猜测。
```

这是一份由可信本地操作者提供的升级输入，没有对应的公开 API。未知角色映射会因外键失败使迁移回滚。
未提供清单也可升级：记录保留并隔离。迁移后没有自动收养隔离数据的接口，需先完成单独的归属核对；
不要直接改库绕过归属不可变约束。

长期记忆仅在所有来源都能指向唯一已确认角色时回填；来源缺失、混合角色、替代记忆归属冲突的记录保留 NULL。
提案、澄清和审计记录继续核验来源及目标归属。旧联系意图的来源无法验证时 ownership_verified=0，
不进入查询或投递；相关旧主动消息也不进入正常会话历史。原始数据保留供核对。
Migration 12 的 DDL、回填、约束及版本标记在同一事务中执行；失败整体回滚。

## 本机 SQLite 实例约束

每个 SQLite 数据库文件只支持一个 Soulseed 后端进程。启动时先取得数据库旁的 `.instance.lock` 文件锁，再执行数据库初始化；关闭时先停止后台任务并记录本实例活动中断，再释放锁。第二个进程会以“数据库已由另一个服务实例运行”拒绝启动。

锁覆盖整个应用 lifespan，不能通过同时运行第二个 Uvicorn 实例、启用多个 worker 或绕开应用 lifespan 来共享同一个数据库。文件锁依赖本机文件系统语义；不支持网络文件系统、多主机或生产级多 worker。

`GET /api/characters/{character_id}/life` 返回活动的 `effective_status`。中断记录保留 `activity_status=active` 作为当时生命周期状态，同时返回 `effective_status=interrupted`、`interruption_reason` 和 `interrupted_at`；API 与聊天上下文不得把它解释为正在进行或已完成。

主动联系偏好分为长期 `allowed`、短时 `busy_until` 和暂时 `pause_until`。明确的恢复联系表达可恢复对应状态；规则只识别有限的中文短语，不具备完整自然语言理解能力。

生活分享保持 `pending`，直到有明确的投递确认。聊天生成只记录渠道选择和短期重试冷却，不推断模型一定提到了该事件；模型失败会释放短期保留。某事件一旦选择聊天渠道，主动联系不会重复消费它。站内联系则在消息实际写入角色会话后才把分享记为 `delivered`。

## 范围与待处理事项

本地文件锁不能协调网络文件系统或多主机部署。聊天模型是否自然提及了注入的分享候选无法从普通文本回复中可靠判断，因此状态保持 `pending`，由渠道隔离和冷却避免跨渠道重复投递；更精确的语义确认需要另行设计可验证的输出协议或明确确认流程。
